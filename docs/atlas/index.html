Orientation

Zicato Atlas

Zicato takes a system under test — source you already have — and proposes changes to it. It runs that system against a board of tasks, scores every run against an evaluation contract, and keeps a change only when the evidence says the system got better.

Eighty-eight concepts, ten drawings and a guided walk through the loop. Start with the map below.

The contract asks for three things, and anything that supplies them can be the subject: an adapter the runner can reconstruct, one or more mutable trees of source the proposer may edit, and a board of tasks carrying typed expectations. Multi-agent systems are the founding use case, but nothing in the loop is agent-specific — a library, a prompt set, or a rule engine fits the same shape.

    Orientation

    What your system must provide

    An adapter, one or more mutable trees of source, and a board of tasks. A system that supplies those three can be the subject, whatever it is built from.

    Where the evidence comes from

    Each epoch declares where its evidence comes from. There are three settings.

    SettingWhat it readsWhat you get
    goldfive
    the default    		 An event stream naming what went wrong during a run. Drift counts and plan revisions, on top of the board's expectations.
    adk_events The agent framework's own events, from a system that never runs under goldfive. What the framework reports, plus the board's expectations.
    transcript The transcript alone. The board's expectations and any in-run judges. The drift term is structurally zero, and a drift-related setting goes inert with a warning rather than a failure.

    The event stream comes from goldfive, an optional dependency. The base install carries the loop and its own telemetry without it, and a test pins that boundary by importing zicato under an interpreter that cannot import goldfive.

    Two consoles, two questions

    Zicato ships its own console, and it answers which candidate won and why: the tournament, the scores, the verdicts, the lineage. Harmonograf answers a different question about the same runs — what one run actually did, step by step, drawn as a Gantt chart with lifelines. Both are read-only views over recorded evidence.

    Orientation

    Run, round, epoch, lineage

    These four words all name some quantity of the loop running, which is why they get swapped for one another. Each one contains the one below it, and each is compared in its own unit: a run against other runs of the same task, a generation against the champion, an epoch against nothing outside itself.

    Lineage
    The cross-epoch graph of every generation ever promoted, and which generation in the previous epoch it descends from.
    one file · lineage.json
    Epoch
    The unit of evaluation contract. The board, the brief's forbidden list, and the scoring weights are frozen for its duration, which is what makes the generations inside it directly comparable. Comparison across epochs is fuzzy by design.
    many rounds · pattern aggregates reset at the boundary
    Round
    One turn of the loop: run, analyze, propose, apply, run the candidate, hold the tournament, journal. A round either advances the generation counter or rejects the proposal and leaves the parent standing.
    many runs · one experiment
    Run
    One execution of the system under test against one board entry, captured as one event stream. The reducer turns it into one loss profile.
    one entry × one generation

    A round contains many runs — one per board entry per generation — so run and round are never interchangeable. A generation is a version of the source; a snapshot is the directory holding that source; a run is one execution of it.

    Mechanism

    One round, step by step

    A round is the smallest complete turn of the loop. It starts with a parent generation standing as champion and ends either with a new champion or with the parent still standing and a recorded reason why the challenger failed.

      Mechanism

      How promotion is decided

      The training-slice gate decides whether a challenger is eligible to replace the champion. It applies its rules in order and returns a provisional promotion only if none of them fires. A separate hidden-holdout confirmation can then revise that provisional result before the round settles.

      → Margin on the scalar score — the challenger must beat the champion by the configured promote margin. A tie fails this rule, and so does a win too small to distinguish from noise, which is what the margin is sized against.
      → Strict monotonicity on pass rate — the challenger must not regress any board entry the champion already passed. An average that improves while a previously-passing entry breaks is a regression, and the gate refuses it.
      → Holdout confirmation, when a holdout is available — a challenger that won on the training slice confirms when it does not meaningfully regress on entries withheld from the process that chose it. A released non-confirmation rejects the challenger; an absent holdout leaves the training verdict unchanged.

      The gate reports a reason on every rejection, naming the rule that fired and the entries involved, and that reason is what the journal and the experiment record carry forward.

      Mechanism

      The hidden holdout, and why it is rationed

      Repeated optimization overfits a fixed board even when every score is measured correctly. Each proposed edit depends on results from earlier edits, so the board gradually becomes training data for the improvement loop itself. Zicato limits that feedback with a hidden slice.

      Tournament selection and the ordinary gate use the training slice. When a challenger would become champion, zicato compares champion and challenger on the holdout. Confirmation does not require a second improvement — it checks that the training improvement generalizes.

      What one query means

      Each final comparison against the hidden slice is one adaptive holdout query. The word comes from statistics: the optimization process asks the hidden data one question about a candidate that earlier results chose. One comparison is one query even when it runs several board entries and makes several model or tool calls. Model calls, tokens, wall-clock limits, and database operations are accounted separately.

      The Ladder governor

      The Ladder limits what repeated queries reveal. It releases a new confirmation only when the training improvement clears its threshold, and charges every consultation against an epoch-level query budget. A withheld result still consumes one query, because the hidden data was inspected either way. Once the budget is exhausted, no further holdout result affects the decision and the training verdict stands.

      The default budget is an operational limit rather than a universal statistical calibration: board size, noise, feedback visibility, and reuse across epochs all still determine how much confidence a holdout supports. The proposer never receives raw holdout entries or per-entry holdout results.

      Using it

      Getting started

      Most workflows need init once and then evolve. Everything else is inspection.

      # 1. Scaffold a workspace next to the source you want improved.
zicato init

# 2. Describe the tasks. One JSON object per line; frozen once the epoch opens.
$EDITOR .zicato/epochs/<epoch>/board.jsonl

# 3. Steer the proposer. Re-read from disk at the start of every round.
$EDITOR .zicato/epochs/<epoch>/brief.md

# 4. Run the loop. It resolves the contract, opens an epoch on any change,
#    and spawns a watchdog plus the console on http://127.0.0.1:7892.
zicato evolve

# 5. Read what happened — in the browser, in the terminal, or on disk.
zicato tui
cat .zicato/epochs/<epoch>/journal.md

      Before trusting a long run, ask whether the loop can see anything at all. zicato health reports whether the evaluation has real optimization signal. A board that every generation passes completely, or fails completely, teaches the proposer nothing, and a loop can run for days in that state while still producing rounds and journal entries.

      The worked example that needs no model anywhere is examples/zicato_examples/target_0_convergence: a deterministic policy adapter whose mutable surface is a single module-level string constant. Every phase of the loop runs against it in continuous integration.

      Using it

      The command surface

      Primary

      zicato initScaffold a fresh workspace. Once per project.
      zicato evolveResolve the contract, auto-open an epoch on any change, and run the loop.
      zicato dashboardServe the console for an existing workspace. evolve already spawns it.
      zicato tuiReview a workspace in the terminal — the console's peer surface, rendering the same served payloads.

      Namespaces

      boardInspect and hand-edit a per-epoch board.
      epochInspect and force epochs. evolve opens them for you.
      proposerScore, diagnose, and improve the proposer itself.
      tournamentRun isolated tournament operations.
      inspectInspect workspace state and derived analysis, including the mutation-surface audit.
      repairRebuild derived and legacy workspace data, such as the analytical index.

      Two tournament modes exist and they are not interchangeable. Full mode re-runs every entry against both generations; fast mode is cache-first and reuses the parent's recorded results. The standalone tournament command defaults to full; evolve defaults to fast.

      Using it

      What it writes to disk

      Every canonical artifact is a human-readable file, because the filesystem is the operator's primary interface. A workspace is meant to be read with ls and cat. 

      .zicato/
  config.json                    # adapter, call_llm wiring, instance id
  epochs/
    {epoch_id}/
      board.jsonl                # frozen for this epoch
      brief.md                   # operator-edited; read fresh each round
      scoring.json               # weights + tournament thresholds
      generations/
        v0/                      # the baseline
          snapshot/              # full source at this generation
          runs/{entry_id}/
            events.jsonl         # one file per run
            loss.json            # reducer output
          gen_score.json
        v1/
          snapshot/
          experiment.json        # hypothesis + patch ids + outcome
          patches/{patch_id}.json
          runs/...
      current_generation         # marker: the promoted head
      patterns/round_{NNN}.json
      loop_health/round_{NNN}.json
      journal.md                 # running narrative
      analysis.md                # written at epoch close
  index.db                       # derived SQLite projection; rebuilt from the files above
  lineage.json                   # cross-epoch generation graph

      A snapshot is a full copy rather than a reference, so copying or deleting one affects no other generation. The one non-text file is the analytical index, and it holds no fact that is not also on disk — zicato repair index reconstructs it in full. The filesystem stays the source of truth; the index is a sidecar that makes cross-run queries fast without walking every file.

      Discipline

      Constraints the loop enforces

      Each of these is enforced somewhere in the system, and each exists because the alternative silently corrupts a result rather than failing loudly.

      The two model callables must differ

      The system under test reaches a model through the target role. Everything zicato itself runs — the proposer, the analysis pass, the multi-turn user emulator, and model-graded expectations — goes through the evaluation role instead. The two must differ by callable identity or by an explicit model override, and zicato refuses to start when they are the same. A user emulator sharing a model with the agent it is interviewing can collude with it, and the resulting score measures nothing. A system under test may use no model at all, in which case only the evaluation role is filled.

      The board is frozen for the epoch

      Editing the board mid-epoch changes the evaluation contract, which is what makes generations inside the epoch comparable. Such an edit requires explicit acknowledgment, and a contract change opens a new epoch rather than silently invalidating the comparisons already recorded. Changing the proposer or its skills rolls the epoch too, because it changes how candidates are generated.

      Every experiment states a hypothesis first

      The proposer's output carries a mandatory structured hypothesis written before the run: the core idea, which mutation points it modulates, the pattern observation motivating it, the drift movements it expects, a pass-rate band, and its risks. A schema-invalid response is rejected and the proposer is re-prompted with the error. Without a prior hypothesis, a journal degenerates into “what changed, what scored”, and nothing can be learned from a rejection.

      Only annotated spans may be rewritten

      The proposer cannot edit arbitrary source. It may only rewrite locations marked as mutation points, addressed by stable id. The applier resolves each patch's id to its location, rewrites the span, and validates that the tree still parses and imports; a patch failing any validator is rejected, and the applier never silently repairs anything.

      Discipline

      Reading the console

      A colour in the console reports what happened to a candidate rather than what role it holds. Green marks an improvement and red marks a regression, so a challenger shows red only when it actually scored worse; being the challenger is never enough on its own. A candidate nothing has scored yet stays neutral.

      ↑Survives — this competitor continues to the next rung or round.
      ✕Cut — this competitor's lane terminates here.
      ○Pending — still racing and undecided. It holds the neutral colour until the gate settles.
      ♛Current champion — the crowned survivor of the gate.
      ♔Former champion — a displaced incumbent, or a round-leader before the gate has decided.
      ◌Unscored — a generation with no parent and no resolved outcome. It gets its own label rather than a verdict it never received.

      On a plot of differences the zero line is the champion's own score, so a point below the line is a lower loss and therefore an improvement. Six colour roles carry the same meaning in all sixteen themes: the ground, the surface a panel sits on, the ink, improvement, regression, and one accent reserved for structure. Because every drawing reads those six rather than a fixed colour, switching theme repaints the page without redrawing anything.

      Deeper treatments live in the repository under docs/design/: start with ARCHITECTURE.md, then VOCABULARY.md for terms, SCORING.md for the gate, OVERFITTING.md for the holdout, MUTATION-SURFACE.md for what the proposer may touch, and CONSOLE-DESIGN-LANGUAGE.md for the visual grammar this page borrows.

      Discipline

      What each figure answers

      The console draws a small set of figures, and each exists to answer one question. They share the marks and colour roles described above, so learning to read one carries over to the rest. Three reading conventions do most of the work, and the drawings below show them.

      Did this round improve on the champion?

      Under the gauntlet structure the round is drawn as lanes measured against a horizontal line at the champion's own score. The line is zero difference, and vertical distance from it is the size of the change.

      Each structure replaces this figure with one shaped like its own competition, and the choice carries a trade-off the repository is explicit about.

      StructureHow it narrows the fieldWhat that costs
      Gauntlet
      the default      		 Each challenger meets the champion directly. Drawn as lanes against the champion's own score. Runs one comparison at a time. Its close correspondence to elitist iterated racing, the mature algorithm for this problem, is why it is the default.
      Racing ladder A small budget to everyone, cut the weakest fraction, repeat. Drawn as a funnel narrowing stage by stage. Concentrates budget on what looks promising. A candidate cut at an early rung is gone even if it lost to variance.
      Swiss Everyone plays every round, paired against contestants on similar scores. Drawn as accumulating Copeland points, with a bump chart of rank where lines cross as the lead changes hands. Ranks a whole field rather than only finding a winner, and pays for it by running every contestant in every round.
      Elimination
      single or double      		 Pair, cut the losers, repeat. Drawn as rounds in columns with lanes converging at each match; double elimination adds a second band where losers re-converge. Defends the budget rather than the result. The repository's own analysis calls this the wrong primitive here.

      That last verdict is worth stating plainly, because the console will draw a bracket for you if you ask. Brackets were built to triage a large field of cheap candidates, and zicato has a small field of expensive, noisy ones where a wrong crowning corrupts the champion that every later round builds on. The evaluation needed to separate two candidates grows as their scores get closer and as the measurement gets noisier, and in that regime the answer is fewer candidates with more evaluation each. That is replication rather than halving, which is what the gauntlet does.

      Is the epoch as a whole getting better?

      One figure answers this directly: a descent with one downward step per round, each step sized by the improvement that round's promotion delivered. A round that promoted nothing is flat.

      Beneath the descent, a timeline lays the same rounds along one horizontal line, a node per round carrying the champion that entered it and that champion's loss. Each round expands into the challengers it minted, a compact picture of how they competed, and the gate's verdict. On the home view a cross-epoch ledger repeats the idea one level up. It draws a staircase of the best score each evaluation contract held, with band width following the generations spent inside that contract. A strip beneath it names which part of the contract changed at each reset: the board, the brief, the scoring, the evaluator revision, the adapter, the mutable trees, the structure, or the proposer. A change of tournament structure draws a dashed boundary there, because floors on either side of it are measuring different competitions.

      Where exactly did this candidate gain and lose?

      A single number says a challenger is better. It cannot say what it traded to get there. The radar answers that: one axis per thing the gate weighs — the scalar, the pass rate, and each named judge's drift — with the challenger drawn as a filled shape against the champion as a dashed one, and outer meaning better on every axis.

      Which board entries moved?

      A single score can improve while individual tasks get worse, so three figures open the aggregate back up.

      Beside the grid, a dot plot gives one row per entry, with its value against the same reference line and an outcome glyph at the right edge. A slopegraph then draws one line per entry running from the champion's value to the challenger's, coloured by whether that entry improved, regressed, or stayed level. The slopegraph is what exposes a raised average that hides a broken task: several lines fall while one climbs.

      Why did this candidate win or lose?

      Two figures trace a single candidate end to end. A lifecycle summary follows it from its parent, through the patch that made it, the fan of board entries it ran, the sum of those results, the gate, and the verdict it terminated in. A causal flow tells the same story with widths, carrying patch into per-entry drift into the gate, so the entries that decided the verdict are the widest bands. Alongside them, a bar per named judge attributes the weighted loss to each one, which is how a failure of process is told apart from a failure of output.

      Is the instrument itself trustworthy?

      Three figures watch the loop rather than the candidates. A calibration trend plots each generation's predicted outcome against its settled one, so a proposer that is consistently overconfident shows as a drift in the running agreement rather than as a hunch. A diversity matrix grids the field against itself, shading how far each pair of challengers overlaps in the mutation points they touch and marking the most overlapping pair. A trajectory strip lays the epoch's edits along their path through the mutation surface, so a loop circling the same few points looks different from one making ground.

      What is happening right now?

      While a round runs, the console draws the field forming and moving. A scalar track shows each contestant's position against the champion's line as results land, with projections in a dashed amber treatment so an estimate never reads as a settled fact. Beside it a proposing tracker lists each challenger as it is minted and whether its patches applied, and a field bar chart gives the gauntlet's contestants as lengths against the champion. All three converge: once the round settles, the live figure and the completed figure render identically. That is a deliberate property, and it is what lets an operator trust a figure they were watching while it moved.

      The small marks

      Inside dense tables the same grammar shrinks rather than changing. A sparkline carries a trend in one cell. A spark bar strip carries a loss profile with a verdict triangle. A row of proportional glyphs carries the pass, fail and timeout counts for a cell. A side-by-side diff puts the champion's text against the challenger's for the span a patch rewrote. Status glyphs render inside a fixed square overlay, so a stretched cell never shears a checkmark into an oval.

      Who has held the crown, and for how long?

      A reign ribbon gives each champion one bar spanning the rounds it held, drawing the current champion in the accent with the solid crown and former champions in dimmed ink with the hollow crown. A lineage figure puts the unbroken line of champions on its own lane and branches rejected challengers into a lower one, so the search itself becomes visible: a long champion line with many short branches is a loop making steady progress against many rejected ideas.

      Every figure scales to the width of its pane through a viewBox, with no panning and no zooming, and an inherently wide table scrolls inside its own box so the page itself never moves sideways. Hovering any mark opens a detail card that reads from the same theme tokens as the figure under it.
